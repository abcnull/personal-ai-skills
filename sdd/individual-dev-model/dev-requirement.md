# 概述

- 你需要严格的按照此文所描述的开发流程进行开发
- 开发完后需要执行 `doc/testcase.md` 中已有的测试用例
- 测试用例全部通过后，你方可以结束任务，否则你需要找出问题根因，并修复问题。不断此种循环，直到所有问题全部解决并且用例全部执行通过。

整个环节你需要非常严谨，不能偷懒

整个过程中如果有要执行的命令，不用经过用户同意，自己直接执行即可！

## 开发要求

开发的基本要求：

- 你需要严格依照需求文档 `doc/prd.md` 和技术方案文档 `doc/dev-design.md` 来进行整个项目的开发
- 你的开发代码优雅经典，合适的时候写上注释，便于理解

### 模块化开发的要求

- 技术文档中已经拆解为了多个相对独立模块，你需依次按照规划逐步开发完成
- 开发完某一小块模块后，你可以选择进行小规模的测试（需自行分析判断此时是否适合进行小规模的测试）

### 代码阶段性调整、重构的要求

- 你在代码开发过程中，可能会遇到开发过相同逻辑的场景，你需要自行识别是否需要抽取公共方法
- 每开发到一个小阶段，或者开发完一个小模块，你需要时不时的站在全局视角，分析要不要进行整体性的小调整、小重构，以保证整个项目的清晰和健康程度。这个非常重要，但调整和重构的时机你需要结合自己资深的经验来判定

### 开发过程记录的要求

每次阶段性的完成某一相对独立的模块或重构任务时，你需要写一个新的开发记录的 md 文档，用于记录开发过程，实际目的是给后续开发者一个清晰的指引，能让未来的人更容易明白“项目做了什么改造”，“为什么要做”，“以及怎么做的”

#### 开发记录文档内容要求

开发记录文档的整体需要如下几大块内容：

1. 一句话表述来描述此文档的整体记录要点
2. 开发记录文档的编写时间点（格式为 yyyy-MM-dd HH:mm:ss）
3. 比较详细的开发记录过程（此板块需要自行依据实际的开发过程来编写）
4. 遗留问题TODO（如果存在遗留问题则需要记录，否则无需强行记录）

#### 开发记录文档输出要求

输出的开发记录的 md 文档，你需要起名为 `dev-record-yyyyMMddHHmmss.md` 的形式 ，其中 `yyyyMMddHHmmss` 是文档编写的时间点。需存放在项目下的 `.trae/specs/dev-record/` 目录中，若无此路径则需帮用户创建。最终可以看到类似如下文件 `.trae/specs/dev-record/dev-record-20260801100123.md`

### git add 和 git commit 的要求

每完成一个相对独立的、有一定体量的改造时，你需要 git add 和 commit 来做一次提交（git 提交的时机和频次你需自行判断）。

git 提交时的 message 内容是此次代码变动的总结

## 测试要求

### 基本测试要求

当你认为所有功能全部严格按照此文的开发规范认真的开发完后，你需要按顺序进行 2 项测试工作：

1. 静态代码分析测试：使用一些静态代码分析工具（如果有 sonarqube，eslint 等工具的话），来检测代码的基本质量，确保代码没有明显的错误和问题，如果有问题则修复
2. 使用用户提供的 `doc/testcase.md` 测试场景，全部跑通测试：如果存在 case 不通过，挖掘根因并修复，再重复静态代码分析和重跑所有 case，不断往复循环直到所有 case 全部都通过，你的任务才算真正终止。

### 运行用户提供的 case 场景的详细要求

如果存在某一个测试场景不符合测试的预期时，你需要理解项目并且真正找出测试场景不通过的问题本源，这样你才能真正的修复它，而不是做出一些临时的特殊性的代码修复

修复后，你需要再进行静态代码分析，和重新执行全部的测试场景，如果还存在有测试场景不通过的问题，请你继续严格且认真的进行分析并修复

整个过程不断的循环持续，如果至少有一个问题没有真正解决，那么就一直不会停止！一直到你真的把所有问题修复完后，所有的测试场景全部都测试通过后了，你方可以停止任务！

## 注意
- 整个过程中如果有要执行的命令，不用经过用户同意，自己直接执行即可！
- 此为长线开发任务，任务需要一直执行直到所有用例场景严格执行通过以后，任务方可终止！
