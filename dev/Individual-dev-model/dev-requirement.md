# 概述

你需要严格此文所描述的开发流程来严格进行开发，开发完后需要执行已有的测试用例，用例全部通过后，你方可以结束任务，否则你需要找出问题所在，并且修复问题，不断此种循环，直到问题全部解决并且用例全部执行通过。

整个环节你需要非常认真严谨，不能偷懒

## 开发要求

基本要求：

- 你需要严格依照需求文档和技术方案文档来进行整个项目的开发
- 你的开发代码优雅经典，合适的时候写上注释，便于理解

### 模块化开发要求

- 技术文档中已经拆解为了多个相对独立模块，你需依次按照规划逐步开发完成
- 开发完某一小块模块（你需自行分析判断此时是否适合进行一小块内容的测试），你可以选择进行小块内容的检测

### 代码阶段性调整,重构要求

- 你在代码开发过程中，可能会遇到开发过相同逻辑的场景，你需要自己识别是否需要抽取出公共的方法
- 每开发到一个小阶段，或者开发完一个小模块，你需要时不时的站在全局的视角，去分析要不要进行整体性的小调整，小重构，以保证整个项目的清晰和健康程度，这个非常重要，但调整/重构的时机你需要结合自己资深的经验自行判定

### 开发过程记录要求

每次阶段性的完成某一相对独立的模块或重构任务时，你需要写一个新的开发记录的 md 格式的文档，用于记录开发过程，实际的目的是给后续开发者一个路径指引，能让未来的人更容易明白“项目做了什么改造”，“为什么要做”，“以及怎么做的”。

#### 开发记录文档内容要求

开发记录文档的整体需要如下几大块内容：

1. 一句话表述来描述此文档的整体记录要点
2. 开发记录文档的编写时间点（格式为 yyyy-MM-dd HH:mm:ss）
3. 比较详细的开发记录过程（此板块需要自行依据是集开发过程记录来编写）
4. 遗留问题TODO（如果存在遗留问题，需要记录，否则无需强行记录）

#### 开发记录文档输出要求

输出的开发记录的 md 文档，你需要起名为 `dev-record-yyyyMMddHHmmss.md` ，其中的 `yyyyMMddHHmmss` 格式是文档编写的时间点。其需要存放在项目下的 `doc/dev-record/` 目录下，如果项目下无 `doc/dev-record/` 目录，则需帮用户创建

### git add 和 git commit 要求

每完成一个相对独立的，有一定体量的改造时，你需要 git add 和 commit 做一次提交（git 提交的时机和频次你需要根据自己的经验来判断）。

git 提交时的 message 是此次改动的信息的总结

## 测试要求

### 基本测试要求
当你认为所有功能全部严格按照此文的开发规范认真的开发完后，你需要按顺序进行 2 项测试工作：
1. 静态代码分析测试
2. 使用用户提供的测试场景，全部跑通测试

你首先要使用一些静态代码分析工具（如果有 sonarqube，eslint 等工具的话），来检测代码的基本质量，确保代码没有明显的错误和问题，如果有问题则修复。

然后需要跑通用户已经提供出来的所有测试场景 case，全部确保测试通过，如果存在 case 不通过，挖掘根因并修复，再重复静态代码分析和重跑所有 case。

不断往复循环直到所有 case 全部都通过，你的任务才算真正终止。

### 运行用户提供的 case 场景的详细要求
如果存在某一个测试场景不符合测试的预期，你就需要认真分析，并解决它。注意你需要理解项目并且真正找出测试场景不通过的问题本源，这样你才能真正的修复它，而不是做出一些临时的特殊性的代码修复

修复后，你需要再进行静态代码分析，和重新执行全部的测试场景，如果还存在有测试场景不通过的问题，请你继续严格且认真的进行分析并修复

整个过程不断的循环持续，如果问题真正解决，那么就一直不会停止！一直到你真的把所有问题修复完后，所有的测试场景全部都测试通过后了，或者是用户直接打断你，要求你停止，这样你方可以停止任务！
